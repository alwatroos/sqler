# ADR-0066: Update check and signed manifest

- Status: accepted
- Date: 2026-10-23
- Deciders: product owner (manifest on GitHub Releases, Ed25519, decision of 2026-10-23), recorded by the SQLer maintainers

## Context and Problem Statement

Version 1.0 ships without an installer that updates itself. Users still need to learn that a newer version exists,
and the answer must not be forgeable: a plain "latest version" file on a web server would let anyone who controls the
network path, or a hijacked host, announce a version and a download link. The check must also be private (no
telemetry, no identifiers), opt-in, and light (one small request, no new TLS stack, no large dependency).

How does SQLer find out, safely, that a newer release exists, without downloading or installing anything?

## Decision

A new headless crate `sqler-update` (layer L1, depends on no other `sqler-*` crate) fetches one signed file, verifies
it and reports `UpToDate` or `Available`. It never downloads a binary and never installs one. Installing is out of
scope for 1.0.

### Feed

The file is a release asset named `sqler-update.json`, fetched from
`https://github.com/alwatroos/sqler/releases/latest/download/sqler-update.json`. GitHub redirects `latest/download` to
the asset of the newest non-pre-release release, so the feed needs no server of ours. The URL is the compiled-in
default (`DEFAULT_FEED_URL`); the client takes the URL as a parameter so tests can point it at a loopback server.

### Envelope format

The asset is a JSON envelope (unknown fields rejected, `format` must be `1`):

```json
{ "format": 1, "key_id": "<16 lowercase hex>", "signature": "<base64 std, 64 bytes>", "payload": "<base64 std of manifest JSON bytes>" }
```

The signature covers `SIGNING_CONTEXT ++ payload bytes`, where `SIGNING_CONTEXT` is `b"sqler-update-manifest-v1\0"`.
The context separates these signatures from any other use of the same key. The payload is the manifest, carried as
base64 so the signed bytes are exactly the bytes verified (no JSON canonicalisation). One asset instead of a detached
`.sig` file means one request and no window in which the two `latest` redirects point at different releases.

The verifier checks in this order: size cap, envelope JSON, `format`, key lookup by `key_id`, base64, signature. Only
after the signature verifies is the payload parsed. A parse failure after a good signature is `Malformed`.

### Manifest

The payload is JSON; unknown fields are ignored so a newer feed can add fields. `schema` must be `1` and `product`
must be `"sqler"`.

| Field | Meaning |
| ----- | ------- |
| `schema` | `1` |
| `product` | `"sqler"` |
| `version` | semver without a leading `v` |
| `published` | RFC 3339 date, informational |
| `notes_url` | `https` link to the release notes |
| `platforms` | map from Rust target triple to `{ url (https), sha256 (64 lowercase hex), size }` |

The `platforms` entries are information for a later installer. 1.0 shows the notes link; the client returns the entry
for its own target (`current_target()`, one of the five release triples) or none. A newer manifest without an entry
for this platform is still offered, with the notes link only. The five triples are `aarch64-apple-darwin`,
`x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`, `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`; the
release work items (R1, R5) may adjust the list in `current_target()` to the artifacts they actually build.

### Signature scheme and keys

Ed25519, verified with `ring`, which is already in the tree (`sqler-tunnel`, `sqler-mcp`, and the TLS stack). No
`ed25519-dalek`, no `rsa`, no `aws-lc-rs`, no new dependency.

- Public keys are compiled in from files in `crates/sqler-update/keys/`. A key file is named `<key_id>.pub` and holds
  one line: base64 of the 32 raw public key bytes. A private key never goes into the repository.
- `key_id` is the lowercase hex of the first 8 bytes of SHA-256 over the raw 32-byte public key.
- This change commits no key file. The list of trusted keys is empty, and `check()` then returns `NotConfigured`
  without any network request. The production key is generated by the team and its public half committed by a normal
  pull request in the release work item (R17). Tests use clearly marked TEST-ONLY seeds that live in the test support
  module and never in `keys/`.
- Rotation: add the new key beside the old one in a release; sign with the new key from the next release; remove the
  old key one release later. A client therefore verifies a manifest signed by either key during the overlap, and an
  old client that missed the new key's release sees `UnknownKey` and keeps working otherwise.

### Check policy

- The check is opt-in and off by default. While the setting is off no request is made.
- The first check runs at least `startup_delay` (30 s) after the first frame, on a background task. It never blocks
  startup or the UI.
- After a success the next check is due after `interval` (24 h). After a failure the delay is
  `min(first_retry * 2^(n-1), max_backoff)` for `n` consecutive failures (1 h doubling up to 24 h).
- The schedule is a pure function of the time passed in (`CheckSchedule::is_due`, `delay_after`); a last attempt in the
  future (clock moved back) counts as due. The numbers are technical defaults and may change in the UI work item (R4).
- A check can be cancelled by dropping the future.

### Request

One `GET` of the feed URL. No query string, no body, no cookies. The only headers are `Host`, `Accept` and
`User-Agent: SQLer/<version> (update-check)`. No identifier, no hostname, no path, no OS detail, no telemetry. The
environment proxy settings are honoured (a corporate user can still reach GitHub), except for loopback hosts, which
bypass any proxy. Timeouts: connect 10 s, whole request 30 s. The body is read with a cap of `MAX_ENVELOPE_BYTES`
(64 KiB); a larger `Content-Length`, or a body that grows past the cap, is `TooLarge`.

The URL must be `https`, or `http` only for a loopback host (tests); it may carry no userinfo, query or fragment.

### Redirect policy

At most `MAX_REDIRECTS` (3) redirects. Each target must be `https`, or `http` on a loopback host only when the feed
itself is loopback. A step from `https` to `http` is never followed. A violation is `Redirect`. There is no host
allowlist: GitHub may change the host behind `latest/download`, and integrity rests on the signature, not on the
transport.

### Errors

Errors are a fixed enum with fixed texts that never contain a URL: `NotConfigured`, `InvalidFeedUrl`, `Offline`,
`Timeout`, `Network`, `Redirect`, `Status(code)`, `TooLarge`, `Malformed`, `UnsupportedFormat`, `UnknownKey`,
`BadSignature`.

### What an attacker can and cannot do

- Forge a manifest: no, without a trusted private key. A signature by an unknown key is `UnknownKey`; a good key id
  with a wrong signature is `BadSignature`.
- Replay or freeze: yes. An old, validly signed manifest is accepted. The client offers only a strictly newer
  version than the running one, so a replay yields `UpToDate` and never a downgrade offer. An attacker who can block
  the feed can keep a user from learning about an update; the manifest carries no expiry in this version.
- Offer a pre-release: no. A manifest whose version has a pre-release part is reported as `UpToDate`.
- Redirect to plain `http` or to a long chain: no, see the redirect policy.

## Consequences

- No new dependency and no new TLS stack. The crate is not linked into `sqler-app` by this change, so the default
  release binary does not change; the UI work item (R4) links it and measures.
- Until R17 commits the public key the client is `NotConfigured` in every build, which is the safe default.
- The release automation (R5) signs the same bytes: it uses `key_id`, `signing_message` and the envelope format from
  `sqler-update`.
- Out of scope: downloading or installing a binary, the settings and notice UI (R4), manifest generation in CI (R5),
  and the production key (R17).

## Note 2026-10-23: settings and notice (R4)

The client is now linked into `sqler-app` and shown in the UI.

- Opt-in: the setting `check_for_updates` in `settings.toml` is `false` by default. While it is off the app makes no
  request, and the manual command shows a hint instead of checking.
- Where: **Settings > Updates** (a switch "Check for updates", a "Check now" button and a status line) and a status-bar
  item. The schedule numbers are unchanged: first check 30 s after the first frame, then every 24 h, backoff from 1 h
  doubling to 24 h after failures. Turning the setting on arms the first check 30 s later, not at once; turning it off
  aborts a check in flight.
- Commands: `app:check-for-updates`, `app:open-release-notes`, `app:dismiss-update-notice`,
  `settings:toggle-update-checks`.
- State file `update-state.toml` in the config directory holds exactly three keys: `last_attempt` (unix seconds),
  `consecutive_failures` and `dismissed_version` (at most 64 characters of `[0-9A-Za-z.+-]`). No URL, path or
  identifier. A bad field falls back to its default.
- Notice: when a newer version is found, the status bar shows `Update <version>` with a dismiss button; opening it
  opens the release notes link (only an `https://` link). Dismissing hides that version from automatic notices across
  restarts; a manual check still shows it. Manual checks also show a toast; automatic failures are silent.
- What is sent: one `GET` of the feed with `User-Agent: SQLer/<version> (update-check)` and nothing else (see
  Request). Nothing is downloaded or installed in 1.0.
- Build: the cargo feature `update` of `sqler-app` is in `default`, because `reqwest`, `ring` and `semver` are already
  linked. `--no-default-features` compiles the client out.

## Rejected alternatives

- A detached `.sig` second asset: two requests, and two `latest` redirects that can race during a release.
- `ed25519-dalek`: a new dependency for something `ring` already does.
- An unsigned feed behind HTTPS only: trusts every hop and the host.
- A host allowlist for the redirect: the host behind `latest/download` is not ours to pin, and the signature already
  carries the integrity.
